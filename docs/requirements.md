## 1. 术语表

| 术语 | 含义 |
|---|---|
| 任务类型（Task Type） | 四类 AI 能力之一：`generate` 生成代码 / `explain` 解释代码 / `debug` 错误分析 / `refactor` 重构 |
| 会话（Conversation） | 一个可命名、可删除的上下文容器，包含多条消息，绑定一个主任务类型 |
| 消息（Message） | 会话中的一轮输入或输出，含 `role`、内容、模型用量、耗时、状态 |
| 片段（Snippet） | 用户显式保存的代码单元，独立于会话长期留存 |
| Provider | 外部大模型服务，通过 OpenAI 兼容协议接入（`base_url` + `api_key` + `model`） |
| 流式（Streaming） | 服务端以 SSE 分块下发模型增量输出，前端逐字渲染 |
| RLS | PostgreSQL Row Level Security，行级权限策略 |
| MVP-1 / MVP-2 | 本项目的两个交付段：MVP-1 为无登录单用户可用版；MVP-2 为接入认证与用户隔离版 |

## 2. 项目背景与定位

### 2.1 要解决的问题

初级开发者使用 AI 编程时，产出物高度碎片化：结果散落在聊天窗口、复制到本地临时文件、报错上下文靠手工拼凑。缺少三样东西——**结构化输入**（语言/任务/约束一次说清）、**可回溯的历史**（这次和上次的差异）、**可复用资产**（写过的代码能存能搜）。

### 2.2 产品定位

面向个人开发者的 **AI 编程任务工作台**：把四类高频任务收敛为固定入口，输出结构化结果（解释 + 代码 + 风险/验证步骤），并将过程沉淀为会话与片段。

### 2.3 一句话边界

> 它是一个"**会写、会讲、会挑错、会整理**"的辅助工具，不是 IDE，不是代码执行沙箱，不对生成代码的正确性作担保。

## 3. 目标与非目标

### 3.1 目标（可度量）

| 编号 | 目标 | 衡量方式 |
|---|---|---|
| G1 | 四类 AI 任务均走真实模型调用，端到端可演示 | 演示时能在浏览器 Network 面板看到 `/api/ai/*` 请求与 SSE 数据流 |
| G2 | 可运行、可构建 | `pnpm dev` 正常启动；`pnpm build` 无错误退出 |
| G3 | 数据持久化 | 写入 Supabase 的会话/片段在刷新页面、重启浏览器后仍可读取 |
| G4 | 安全基线达标 | 仓库与前端产物中搜不到 API Key；MVP-2 下跨用户访问返回 403/404 |
| G5 | 有真实测试记录 | 单元/集成/e2e 均有实际执行输出，失败项如实记录 |
| G6 | 可用于简历与面试 | README + 架构图 + 截图/视频 + 能在 5 分钟内讲清 3 个技术决策 |

### 3.2 非目标（明确不做）

| 编号 | 不做的事 | 理由 |
|---|---|---|
| N1 | 在服务端执行用户提交的代码 | 沙箱隔离是独立工程量，安全风险高；第一版只做分析建议 |
| N2 | 多智能体编排、RAG 向量检索、代码库索引 | 对 MVP 无增益，显著抬高复杂度 |
| N3 | 团队协作、分享链接、公开片段广场 | 引入权限模型复杂度，非本期价值点 |
| N4 | 付费计费、模型微调训练 | 与"个人作品集项目"目标无关 |
| N5 | 移动 App、浏览器插件、IDE 插件 | 单一 Web 端已足够演示 |
| N6 | GitHub 仓库同步、自动提 PR | 需 OAuth 与仓库权限，风险与收益不匹配 |
| N7 | 对生成代码的正确性作担保 | 产品输出是"建议"，需明示免责 |

## 4. 用户与场景

### 4.1 用户画像

- **P1（主）**：本人。计算机专业大三，掌握语法但缺工程经验。既是使用者，也是演示者与讲解者。
- **P2（次）**：同类初级开发者。特点是"知道自己要什么，但不知道怎么写规范"。

### 4.2 核心用户故事

| 编号 | 场景 | 期望结果 |
|---|---|---|
| US-1 | 课程作业要写防抖函数，不确定 TS 类型怎么写 | 选 TypeScript + 生成 + 约束"零依赖、含泛型、带注释"，拿到可直接用的代码 |
| US-2 | 拿到一段别人的 Redux 中间件代码，看不懂执行顺序 | 粘贴后得到"用途 / 执行流程 / 关键函数 / 数据流"四段式解释 |
| US-3 | 运行报 `TypeError: Cannot read properties of undefined (reading 'map')` | 贴代码 + 报错 + 环境，得到按可能性排序的原因、出错行定位、修复后代码与 diff、验证步骤 |
| US-4 | 一个 200 行函数职责混乱 | 选择重构目标（拆分函数 + 改善命名），拿到前后对比与兼容性影响说明 |
| US-5 | 上周写的 JWT 校验代码找不到了 | 在片段库搜索关键词、按语言筛选，找到后一键复制 |
| US-6 | 对上一轮结果不满意，想追加要求 | 在同一会话内继续追问，模型能看到前几轮上下文 |

### 4.3 主流程（文字版）

```
进入工作台
  → 选择任务类型（生成/解释/调试/重构）与编程语言
  → 输入需求或粘贴代码（调试需额外填报错信息）
  → 提交（前端校验 → 服务端校验 → 限流检查）
  → SSE 流式返回，界面分区块渲染（解释 / 代码 / 风险与验证）
  → 复制代码 / 重新生成 / 继续追问
  → 一键保存为片段 → 会话自动入库，可回溯、可搜索
```

## 5. 范围与分期（关键决策）

### 5.1 四段式交付

| 阶段 | 时间 | 范围 | 出口标准 |
|---|---|---|---|
| M0 骨架 | 第 1 周 | 项目初始化、设计系统、首页、工作台静态骨架、主题 | 页面可导航，`build` 通过，未配置 Key 时显式提示"AI 未配置"而非返回假数据 |
| M1 AI 核心 | 第 2 周 | 适配层、四类任务、流式、错误分类与重试、限流 | 四类任务真实返回；断网/超时/401/429 均有可读提示 |
| M2 数据与测试 | 第 3 周 | 会话、上下文裁剪、片段 CRUD、搜索分页、单测/集成/e2e | 刷新不丢数据；测试有真实执行记录 |
| M3 安全与交付 | 第 4 周 | Supabase Auth、RLS、接口鉴权、部署、文档、演示素材 | 跨用户越权被拒；线上链接可演示；README 完整 |

### 5.2 决策 D1：单用户 MVP → 多用户（两段式）

**决策**：M0–M2 为无登录单用户版，全部数据归属服务端固定的 `DEFAULT_WORKSPACE_ID`；M3 引入 Supabase Auth，数据写入 `owner_id` 并开启 RLS。

**理由**：认证与 RLS 会拖慢 AI 主链路的验证节奏，而 AI 链路才是这个项目的核心可讲点。先跑通价值，再补权限。

**代价与约束（必须写进 README 的 Known Limitations）**：
1. M0–M2 版本**没有用户隔离**。任何人拿到链接都能看到同一份数据。
2. 因此 M0–M2 **不得部署为公开可访问地址**；如需线上演示，先完成 M3。
3. M2 阶段的接口虽无登录态，但**禁止**把 Supabase `service_role` Key 下发到客户端；所有数据库访问只走服务端。
4. RLS 在 M2 起即**默认拒绝 anon 访问**，为 M3 的策略切换预留一致语义。

### 5.3 其它技术决策（需求层约束，不写实现）

| 编号 | 决策 | 理由 |
|---|---|---|
| D2 | 不引入 ORM，用 Supabase JS Client + 手写 SQL migration | 依赖少；RLS 必须手写 SQL 才能真正讲清楚，是面试可讲点 |
| D3 | 不引入全局状态库（Redux/Zustand） | 工作台状态以"当前会话 + 当前输入"为主，React 内置状态 + 少量 Context 足够 |
| D4 | 流式用手写 SSE（Route Handler + `ReadableStream`），不套 AI SDK | 约 80 行可控代码，边界（超时/中止/错误帧）自己掌握，便于讲解；若时间不足可作为降级选项重新评估 |
| D5 | 输出结构化：模型返回 Markdown，代码块用 ` ```lang ` 围栏，前端解析渲染 | 比强制 JSON 更抗模型输出漂移，解析失败时降级为纯文本渲染 |

## 6. 功能需求

优先级定义：**P0 = MVP 必须有**，P1 = 有余力才做，P2 = 本期不做（仅登记）。

### F1 工作台与导航

| 编号 | 需求 | 优先级 | 验收要点 |
|---|---|---|---|
| FR-1.1 | 首页：产品一句话定位、四项核心能力、开始使用入口、技术栈说明 | P0 | 入口按钮跳转到 `/workspace` 且可新建会话 |
| FR-1.2 | 工作台三区布局：左侧会话列表 / 中部对话与输入 / 右侧代码与结果 | P0 | 三区可独立滚动；折叠侧栏后布局不塌陷 |
| FR-1.3 | 任务面板：任务类型 Tab、语言下拉、约束文本框 | P0 | 切换任务类型时输入区的字段随之变化（调试多一个"报错信息"框） |
| FR-1.4 | 响应式：≥1024px 三栏；768–1023px 两栏（侧栏可抽屉）；<768px 单栏 + 底部 Tab | P0 | 三种宽度下无横向滚动条、无元素重叠 |
| FR-1.5 | 主题：浅色 / 深色 / 跟随系统，可持久化 | P0 | 刷新后保持；无闪烁（FOUC）；深色下对比度可读 |
| FR-1.6 | 四类状态：loading（骨架/流式光标）、empty（引导文案+示例）、error（可重试）、success（Toast） | P0 | 每个状态都有真实触发路径，不是静态样式 |
| FR-1.7 | 所有展示的主按钮必须真实可用 | P0 | 无 `alert('TODO')`、无 `href="#"` 占位；未实现的功能必须隐藏或置灰并给出说明 |

### F2 AI 代码生成（generate）

| 编号 | 需求 | 优先级 | 验收要点 |
|---|---|---|---|
| FR-2.1 | 自然语言需求输入，长度 1–8000 字符 | P0 | 空输入与超长在前端即拦截；后端 Zod 二次校验，返回 400 与字段级错误 |
| FR-2.2 | 编程语言选择：TypeScript / JavaScript / Python / Java / Go / SQL / HTML+CSS / 其它（选"其它"时需填名称） | P0 | 选择结果随请求发送并体现在 Prompt 中 |
| FR-2.3 | 额外约束输入（风格、依赖限制、输出要求），≤500 字符 | P0 | 约束为空时不注入空段落 |
| FR-2.4 | 调用真实模型 API，服务端完成鉴权与调用 | P0 | Network 中可见服务端请求；前端无任何模型 Key |
| FR-2.5 | 结果分区展示：说明（Markdown）/ 代码（带语言标识、行号、语法高亮）/ 依赖与运行说明 | P0 | 代码块可独立滚动；语言标签与所选语言一致 |
| FR-2.6 | 复制代码、重新生成、继续追问 | P0 | 复制成功有 Toast；重新生成产生新消息且保留上一条；追问携带上下文 |
| FR-2.7 | 流式输出，首字节 ≤3s（正常网络，不含模型排队） | P0 | 逐字渲染过程中可"停止生成" |
| FR-2.8 | 输出长度上限（`max_tokens` 可配置，默认 2048） | P0 | 达到上限时标注"输出被截断"，不静默截断 |
| FR-2.9 | 输入超限、超时、失败、模型返回异常的分级提示 | P0 | 每类错误有独立文案与可操作建议（重试/检查配置/稍后再试） |

### F3 AI 代码解释（explain）

| 编号 | 需求 | 优先级 | 验收要点 |
|---|---|---|---|
| FR-3.1 | 粘贴代码，≤12000 字符，可选"想重点关注什么" | P0 | 超长拦截并提示拆分 |
| FR-3.2 | 输出固定四段：用途概述 / 执行流程（按段落推进） / 关键函数与数据结构 / 输入输出数据流 | P0 | 四段齐全；缺失段落时标注"模型未给出" |
| FR-3.3 | 逐段解释 | P0 | 按函数边界/空行启发式切分代码并逐段对应；切分不精确时允许整体解释，但需说明限制 |
| FR-3.4 | 面向初学者的语言，术语首次出现给出简短解释 | P0 | 抽查 3 个样例，无未解释的缩写堆砌 |
| FR-3.5 | 区分"已知事实 / 推测 / 需进一步验证" | P0 | 涉及外部库行为、运行时版本差异时必须归入推测或待验证 |

### F4 错误分析与修复建议（debug）

| 编号 | 需求 | 优先级 | 验收要点 |

### F9 设置

## 9. 技术选型与理由

| 层 | 选型 | 理由 | 主要风险 |
|---|---|---|---|
| 框架 | Next.js（App Router）+ React + TypeScript `strict` | 前后端同仓、Route Handlers 免单独服务、Vercel 一键部署 | App Router 的缓存/流式语义易踩坑，需按实际版本文档处理 |
| 样式 | Tailwind CSS + shadcn/ui + Lucide | 组件源码在仓库内可改可讲，不引入黑盒 UI 库 | shadcn CLI 与 Tailwind 大版本需匹配 |
| 校验 | Zod | 同一份 schema 前后端复用 | 需注意前后端错误对象结构差异 |
| 数据库 | Supabase PostgreSQL | 免费额度足够、控制台可视化、RLS 是加分讲点 | 免费项目长时间不活跃会暂停，演示前需唤醒 |
| 认证 | Supabase Auth（M3） | 与 DB/RLS 天然打通，省自建 JWT | 邮件确认流程可能阻塞注册，需配置 |
| AI | OpenAI 兼容适配层（`base_url`/`api_key`/`model`） | 换供应商零改代码；DeepSeek、通义千问、智谱均提供兼容端点 | 各供应商流式细节与错误码不完全一致，需在适配层归一 |
| 测试 | Vitest + React Testing Library + Playwright | 与 Vite/Next 生态一致；e2e 覆盖真实链路 | e2e 依赖真实网络与数据库，需可控的测试数据 |
| 包管理 | pnpm | 安装快、磁盘占用低 | Windows 下需确认已安装 |
| 部署 | Vercel | 与 Next 原生集成、免费 HTTPS 域名 | Hobby 计划函数执行时长受限，长响应需流式或降级 |

**版本策略**：不在需求阶段锁定具体版本号。任务 2 环境检查后，以**实际可安装且相互兼容**的版本为准，写入 `package.json` 并提交 lock 文件；不使用记忆中未经验证的 API。

## 10. 非功能需求

| 编号 | 类别 | 要求 |
|---|---|---|
| NFR-1 | 类型安全 | `strict: true`；禁止 `any`（ESLint 报错级）；外部输入一律经 Zod 解析后才进入业务层 |
| NFR-2 | 分层 | Route Handler 只做「鉴权 → 校验 → 编排 → 响应」；业务逻辑在 `lib/`；UI 组件不直接调用 Provider |
| NFR-3 | 可测试 | 纯函数（Prompt 组装、上下文裁剪、错误映射、代码块解析）单测覆盖 ≥70%；关键链路有 e2e |
| NFR-4 | 安全 | Key 仅服务端；`.env.local` 不入库；不执行用户代码；响应头基础加固；RLS 默认拒绝 |
| NFR-5 | 性能 | 首页 LCP <2.5s（近端网络）；工作台交互响应 <100ms；AI 首字节 <3s（不含模型排队） |
| NFR-6 | 可用性 | 键盘可达、focus 可见、图标有 `aria-label`；深浅色对比度满足可读 |
| NFR-7 | 成本控制 | 输入长度上限 + `max_tokens` 上限 + 限流 + 单会话串行 |
| NFR-8 | 容错 | AI 失败不清空用户已输入内容；流式中断保留已生成部分并标注"未完成" |
| NFR-9 | 可观测 | 结构化日志：`requestId`、`task_type`、`latency`、`status`、`error_category`；不含敏感信息 |
| NFR-10 | 诚实性 | 未实现的功能在 UI 与文档中如实标注；不以 mock 数据冒充真实 AI 结果；不通过关闭类型检查/删除测试来"通过"验收 |
